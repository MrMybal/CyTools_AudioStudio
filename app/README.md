# CyTools_AudioStudio — developer guide

Standalone audio studio built on the CyToolsCore SDK 0.10.1 (public, MIT: https://github.com/MrMybal/CyToolsCore): a multitrack editor with per-track
insert chains (106 native effects, 92 of them real-time, and VST3 plugins) with their own
interfaces, automation lanes, a master bus, saved workflows (tail rendering included),
sound-effect, music and voice generation with several models, voice presets, an optional text
assistant for TTS annotations, mastering, and a model/engine installation screen. One runtime serves the Dear ImGui interface,
the CLI and MCP. It replaces CyTools_AudioGen, CyTools_ACE-Step1.5, CyTools_FishSpeechS2Pro,
CyTools_Piper_TTS and CyTools_Qwen3-TTS, whose weights were moved here (see
`data/reports/migration-legacy.json`).

## What the git repository contains

Only the source tree is versioned: `app/` (code, manifest, interface, workers, tests, docs,
scripts, model catalogue), the root launchers (`CyTools_AudioStudio.sh`, `app/launcher.cpp`) and
the user guide. `.gitignore` excludes `data/` (model weights, jobs, sessions, presets, settings,
logs, reports — about 44 GB of weights on the author's machine), `runtime/` (private Python,
engine environments, vendored sources, backups), the compiled `CyTools_AudioStudio.exe` and
Python bytecode. A fresh clone is rebuilt with the installation steps below; models are then
installed from the Models tab or with `install_model`. Nothing under `data/` is ever needed to
build or test the application: the test-suite uses synthetic fixtures only.

## Operations (40)

Processing: `process_audio`, `batch_process`, `convert_audio`, `analyze_audio`, `master_audio`, `render_session`
(mix a saved editor session with its inserts, automation and master bus, tail included), `edit_session`
(scripted session editing: add / replace / remove tracks, chains, master, tail, save, render), `batch_session`
(one render per input sound placed in a slot track of a session), `list_effects`
(`realtime` and `sidechain` flags per effect), `list_workflows`, `get_workflow`, `save_workflow`, `scan_plugins`,
`list_plugins`, `describe_plugin`.
Generation: `generate_sfx` (backends `sfx_procedural`, `audioldm`), `preview_sfx_recipe`, `list_sfx_types`,
`generate_music`, `remix_music`, `repaint_music`, `write_lyrics` (backend `acestep`).
Voices: `voice_piper`, `voice_qwen3tts`, `voice_fishspeech`, `generate_voice` (from a preset), `prepare_tts_text`,
`list_voices`, `save_voice_preset`, `list_voice_presets`, `delete_voice_preset`.
Models and engines: `list_models`, `install_model`, `verify_model`, `remove_model`, `engine_status`, `install_engine`,
`diagnose_backend`, `release_workers`, plus `installation_storage_status` from the SDK.

Every generation operation accepts `post_workflow` (name of a saved workflow) applied to the result
with tail rendering. `generate_sfx` needs `backendId`.

### Workflows and tail rendering

A workflow is a JSON document (`data/workflows/<name>.json`, format `cytools-audiostudio-workflow`)
with nodes of kind `effect`, `vst3` (plugin path + parameters + opaque state) or `model`, each with
`enabled` and `mix`. `tail` = `{enabled, threshold_db, max_seconds, hold_seconds}`: the engine appends
`max_seconds` of silence before a chain that contains a stateful node, renders, then trims what is
below `threshold_db` after the original length (never shorter than the input). A selection processed
in the editor overlaps its tail onto the following audio.

### Tracks and clips: trim, fades, moves, navigation

A `Track` (`editor/document.py`) is a lane: mixer settings, insert chain, automation and a list of
`Clip`s, all rendered through that chain (`Renderer.clip_block` sums them, overlaps included). A clip
keeps all its decoded audio and shows the window `audio[:, start:start + length]` at `offset`.
Dragging an edge only moves that window, so trimming is reversible; `Clip.flatten()` bakes it in and
runs before any edit that rewrites samples (delete, paste, effects). `fade_in` / `fade_out` are seconds
applied by `Document._fade_gain` at mix time, so they cost nothing and stay editable. Region edits work
clip by clip (delete and insert ripple the following clips of the track); `split()` cuts the clip under
the cursor in two clips of the same track without rewriting audio. `add_clip` puts a sound on an
existing track (after its last clip when the place is taken: that is what a file dropped on a track
does), `move_clip` moves one in time and/or to another track (one undo entry covering both tracks),
`remove_clip` / `duplicate_clip` / `reverse_clip` (whole material reversed, window mirrored: trimmed audio kept) back the right-click menu. `Track.offset` / `end` / `frames` span all
the clips; `Track.audio`, `start`, `length`, `fade_in`, `fade_out`, `source` read and write its first
clip, for code written when a track was one clip. Sessions schema 3 store each clip (complete material
plus `start`, `length`, `fadeIn`, `fadeOut`, `offset`); schema 2 sessions (one clip per track) load as
tracks with one clip. Horizontal navigation: wheel zoom, Shift+wheel, middle-drag, Space+drag, or the
scrollbar under the lanes. The toolbar groups (`gui/widgets.Toolbar`) are framed and titled and wrap
to the next line when the window is narrow.

### Track inserts, master bus, automation

Every track and the master bus own an insert chain (`Track.inserts`, `MasterBus.inserts`): the same
node format as workflows (`effect` / `vst3`, `params`, `state`, `enabled`, `mix`, plus an optional
`sidechain` track id). `editor/renderer.py` renders the graph block by block: clip (with fades) ->
stereo upmix -> inserts -> volume/pan (static or automated per frame) -> sum -> master inserts ->
master gain. The player owns one `Renderer` for real-time playback; `Document.mixdown()` creates a
fresh one for exports and `render_session`, and keeps rendering silence after the end until stateful
inserts are below `Document.tail['threshold_db']` (never cut). Native effects are `Processor`
subclasses (`dsp/processors.py`) whose parameters change live without resetting their state; JUCE
effects and VST3 plugins are wrapped with a FIFO that absorbs their latency. A processor that raises
is bypassed and its message shown in the inserts panel; the audio thread never dies.

Automation lanes (`editor/automation.py`) are breakpoints in the parameter's own unit, keyed
`gain_db`, `pan`, `mute` or `<node id>.<param>`; insert parameters are evaluated once per block,
volume/pan/mute per frame. "Write automation" records knob and slider moves while playing.
Sessions (schema 3) store clips, inserts, lanes, the master bus and the tail settings; schema 1 and 2
sessions still load. `Document.bake` (inserts panel "Bake") renders a chain into the clip with its tail.

Effect interfaces (`gui/effect_ui.py`) share a header with input/output meters and a live scope of
the audio around the node, then a family view: dynamics (transfer curve, gain-reduction meter and
history), multiband (draggable crossovers over the spectrum, per-band compressors), parametric EQ
(draggable bands over the live spectrum), graphic EQ, filters (response curve), reverbs (decay
envelope), delays (echo taps), modulation (LFO), distortion (transfer curve), vocoder (band levels),
stereo (goniometer), analyser (spectrum, goniometer, peak/RMS/correlation), dynamic EQ (bands with their
live gain change over the spectrum), loudness meter (momentary / short-term / integrated LUFS, history
with the -14 and -23 LUFS targets), noise reduction (input spectrum against the noise threshold, learn
mode), step pattern (16 clickable steps with the playing step), pitch correction (detected pitch, target
note, correction gauge) and a generic knob view.
Presets of native effects live in `data/presets/effects/<effect>/`, VST3 presets (parameters + state)
in `data/presets/plugins/<plugin>/`.

### Headless sessions: scripting and batches (CLI / MCP, Linux-ready)

A session is a folder (`session.json` + one WAV per track) and every editor concept has a headless
counterpart in `audiostudio/editor/batch.py`, exposed by two operations that run through the same
runtime and DSP worker as the interface:

- `edit_session` applies a list of actions to an existing session (or a new one), saves it under
  `data/sessions/<name>` (or an absolute folder) and can render the mix in the same call. Actions:
  `add_track` (file, name, offset_seconds, gain_db, pan, mute, solo, `inserts_from` another track,
  `workflow_name` or inline `nodes`), `replace_audio` (keeps the track's chain, lanes, gain and pan),
  `remove_track`, `set_track`, `set_inserts` (track or `master`), `set_master`, `clear_automation`,
  `set_tail`. Tracks are addressed by id or exact name.
- `batch_session` renders a session once per input sound: each sound is placed in a *slot* track — an
  existing placeholder track whose audio is replaced (its inserts, automation, gain and position are
  kept) or a new track created from `inserts_from` / `workflow_name` — the mix is rendered with the tail
  to `output_dir` (named after the sound plus `suffix`), then the next sound takes its place. `solo`
  renders the slot alone. A missing sound is reported in `failed` and the batch continues.

The interface prepares the project (bed tracks, a placeholder track with its chain, master inserts),
`Save session` writes it, then a script drives the batch. On Linux the same commands use
`runtime/python/bin/python` (never executed by the author; see Limits):

```bash
PY=runtime/python/bin/python          # Windows: runtime\python\Scripts\python.exe
$PY app/tool.py invoke batch_session --params '{
  "session": "/srv/audio/data/sessions/voice-template",
  "inputs": ["/srv/sounds/a.wav", "/srv/sounds/b.wav", "/srv/sounds/c.wav"],
  "slot": {"track": "Voice", "offset_seconds": 0.5},
  "output_dir": "/srv/renders", "suffix": "_mix", "output_format": "wav"}'
# or step by step, one sound at a time (replace, render, next):
$PY app/tool.py invoke edit_session --params '{"session": "/srv/audio/data/sessions/voice-template",
  "actions": [{"action": "replace_audio", "track": "Voice", "file": "/srv/sounds/a.wav"}],
  "render": true, "output_format": "wav"}'
```

Inputs must be absolute paths (the SDK imports them into the job workspace; relative paths are refused).
`edit_session` returns the description of the session after the actions (tracks, chains, lanes, master,
tail) so a script can inspect what it built; `batch_session` returns one entry per rendered file.
Through MCP the same two tools (`op_edit_session`, `op_batch_session`) let an assistant script the
editor.

### Voice presets

`data/presets/voices/<id>.json`: backend, model, every parameter except the text, reference
recordings with SHA-256, optional post workflow. `generate_voice {preset, text}` regenerates the
same voice; a changed reference is reported as a warning.

## Engines and workers

`engines.json` declares two environments: `torch` (torch 2.8.0+cu128, transformers 4.57.3,
diffusers 0.37.1, qwen-tts 0.1.1, Fish Speech and ACE-Step stacks; vendored sources at pinned
revisions) and `piper` (piper-tts 1.8.0, onnxruntime). Workers are persistent processes with a
JSON-lines protocol (`workers/_protocol.py`, `audiostudio/engines/workerhost.py`): handshake,
progress and log events, cancellation by process kill, idle unload, one resident GPU backend at a
time (`WorkerPool.make_exclusive`). The manifest also declares SDK 0.10 `exclusiveGroups`
(`EXCLUSIVE_GROUPS` in `build_manifest.py`): `gpu` for every operation that loads a model on the
graphics card, `engine_torch` / `engine_piper` so that `install_engine`, `release_workers` and
`diagnose_backend` never run beside an operation of that engine, `model_files` between model
installation / removal and generation. With the current `Sequential` policy they change nothing;
they are what keeps these operations apart if the policy is ever raised. The runtime status
(`GetRuntimeStatus`) counts the worker hosts as running or stopped through their process, never as
unknown (`tests/test_runtime.py`). This persistent-worker host is a generic extension candidate for
the SDK (its `ProcessWorker` is one-shot and has no progress channel).

```powershell
git pull
.\runtime\python\Scripts\python.exe -m pip install "cytools-core[mcp] @ git+https://github.com/MrMybal/CyToolsCore.git@a8d200f2d0baaade1633e0683663b4506c595f74"
```

The engines (`runtime/engines`), the vendored sources and the models are untouched: they do not
import the SDK.

**Updating a portable installation**: the runtime ABI changed, so the Updates tab refuses the
application stream of 0.1.1 on a 0.1.0 installation (its `runtime/python` still holds the GPL SDK
0.9.0). Unzip `CyTools_AudioStudio-0.1.1-win64.zip` next to the old folder, then move `data/` and,
when engines were installed, `runtime/engines` and `runtime/sources` into the new folder. Later
releases with the same ABI are installed in place by the Updates tab, which also refreshes
`LICENCES/` (the files it replaces are kept beside the application backup).

**Going back to 0.1.0**: keep the old portable folder, or from source:

```powershell
git checkout v0.1.0
.\runtime\python\Scripts\python.exe -m pip install "cytools-core[mcp] @ git+https://github.com/MrMybal/CyToolsCore.git@442f537"   # SDK 0.9.0, received under the GPL-3.0
```

The SDK 0.9.0 still loads the manifest of 0.1.1 (it ignores `exclusiveGroups`), but `LICENCES/`
would then describe an SDK that is not the installed one: the application and the SDK go back
together.

for a venv, `runtime/python/` for the portable build). `publish_release.py` creates the GitHub release

## Limits

- Windows x64 with an NVIDIA GPU is the only executed platform. Linux launcher and CPU-only
  PyTorch build are provided but were not run; the headless batch (`edit_session`, `batch_session`)
  uses only numpy / scipy / pedalboard / soundfile and `pathlib`, no Windows-specific code, but it was
  validated on Windows only (WSL is not installed on the author's machine).
- VST2 is not supported (no licence). VST3 instruments (MIDI) are not exposed. Plugins are hosted
  through pedalboard/JUCE; a plugin that needs a window to initialise may fail to scan.
- ASIO is not available: the bundled PortAudio has no ASIO backend and the Steinberg SDK licence is
  not held. Playback and recording use WASAPI/DirectSound through sounddevice.
- Real-time: 92 of the 106 native effects run as inserts. `pitch_shift` (Rubber Band streaming
  returns nothing; `pitch_shifter` is the granular real-time alternative), `time_stretch`, `normalize`, `loudness`, `noise_reduction`, `resample`, fades,
  `reverse`, `trim_silence`, `add_silence`, `channels` work on whole buffers only (selection effects
  and workflow nodes). The interface hosts VST3 inserts in its own process for real-time playback:
  a plugin that crashes takes the interface with it (scanning and the plugin window stay in the
  worker). No oversampling in the saturation effects; no VST3 instruments.
- The runtime reserves VRAM against the free memory measured at start: other GPU applications
  (ComfyUI, Unreal) reduce what the Tool can run; Fish Speech needs ~20 GB free.
- The text assistant (Qwen3-1.7B) annotates paragraph by paragraph and falls back to the heuristic
  when it changes the words; it is optional.
- The application update stream points at `MrMybal/CyTools_AudioStudio` (release.json); no release has
  been published there yet, so the update path is verified with fixtures only (a check against the
  repository answers "not found" until it is public and carries a release).
